- **`VertexPositionIndex.java`** — open-addressed exact-position → vertex-index table (negative zero

### Why three arrays, not two

`faceOrigin` answers "is this face an untouched copy of an input triangle, and if so whose"
(`ORIGIN_A` / `ORIGIN_B` / `ORIGIN_NEW`). `faceSourceOperand` answers "whose surface does this face
lie on" and is never `ORIGIN_NEW` — every output triangle of a boolean between two closed solids
lies on one operand's surface. `faceSourceQuad` is the input **quad** id within that operand.
Downstream consumers (CRAW-14 textures, CRAW-15 attributes, MESH-50 weld) need the second and third
even for cut faces; only the dirty-patch marking needs the first.

### How a face is attributed

1. `manifold_as_original` stamps each operand, giving it an original id (3 and 4 for the two cubes)
   and initialising Manifold's coplanar `faceId` grouping.
2. The result's `runIndex` / `runOriginalId` partition output triangles by originating operand →
   `faceSourceOperand`.
3. Each output triangle's three corners are looked up by exact position in the operand's vertex set
   (`VertexPositionIndex`); if all three resolve and share one input triangle, the face is an
   untouched copy → `faceOrigin` = that operand, `faceSourceQuad` = that triangle's source quad.
4. Otherwise the face is a piece the intersection curve cut → `faceOrigin = ORIGIN_NEW`, and the
   source quad comes from the triangle's `faceId` coplanar group, resolved to the group member whose
   plane best contains the output triangle's centroid (largest minimum barycentric coordinate).

Step 4 is the "nearest-source fallback" the ticket's second unknown anticipated. It is exercised:
on the two-cube fixture every single `ORIGIN_NEW` face resolves to a source quad (unresolved = 0 for
all three operations).

## The C1 side question: why did the old backend report `faces new=0/36`?

The old classifier lived at commit `becea043` (`decodeProvenance`, later deleted in `16e99787`
which reduced the backend to `new MeshBooleanResult(mesh, new int[0], new int[0])`). It did:

```java
Arrays.fill(faceOrigin, MeshBooleanResult.ORIGIN_NEW);
for (int run = 0; run < runOriginalId.length; run++) {
    ... if runOriginalId[run] == originalIdA -> origin = ORIGIN_A; else if ... B ...
    for (int triangle = firstTriangle; triangle < endTriangle; triangle++) {
        faceOrigin[triangle] = origin;   // overwrites the ORIGIN_NEW prefill
```

so a face stayed `ORIGIN_NEW` only if it fell in **no** run, or in a run whose `runOriginalID`
matched neither operand. Neither ever happens. Dumped live from the current bindings for the
two-cube union (scratch probe, output reproduced verbatim):

```
originalId A=3 B=4
triangles=36 vertices=20
runIndex=[0, 54, 108]
runOriginalId=[3, 4]
faceId.length=36 faceId=[0,1,0,3,1,3,4,4,5,5,4,5,9,9,4,9,5,9,0,1,0,3,0,0,1,3,1,1,3,3,4,5,4,9,5,9]
```

`runIndex` is in **corners**: run 0 covers corners 0–53 = triangles 0–17 (all tagged original 3 = A),
run 1 covers triangles 18–35 (original 4 = B). The two runs tile all 36 triangles with no gap, so
the prefill was overwritten 36 times out of 36 → `new=0/36`. The `36` in the log is exactly this
fixture's union triangle count, which is why the number matched.

The deeper point is that **Manifold's run table has no "new" category and structurally cannot have
one**. A run names the originating *solid*, and Manifold keeps that attribution for the whole
retained surface of each operand — including the sub-triangles it produces when it retriangulates a
face the intersection curve cut. The boolean of two closed solids never emits surface belonging to
neither operand, so "in no run" is unreachable by construction. Run membership alone can therefore
answer "which cube" but never "was this face split". Distinguishing an untouched copy from a cut
piece requires comparing output geometry against the input triangles, which is what
`BooleanFaceProvenance` now does (step 3 above).

Two secondary defects in the same old code, for the record: the `cornersPerEntry` heuristic
(`runIndex[last] == triangleCount ? 1 : THREE`) happened to pick the right unit here (108 ≠ 36 → 3),
and `faceID` was used as a direct index into `operand.triangleSourceFace` even though it is a
coplanar-**group** id (values `{0,1,3,4,5,9}` above — six groups, one per cube quad, each id being
the group's first triangle), not a per-triangle input index. Neither was the cause of `new=0`.

### A / B / NEW face counts on the two-cube fixture

Measured with a scratch probe against the built classes:

| op | faces | origin A | origin B | origin NEW | sourceOperand A | sourceOperand B | sourceQuad unresolved |
|---|---|---|---|---|---|---|---|
| UNION        | 36 | 6 | 6 | 24 | 18 | 18 | 0 |
| DIFFERENCE   | 24 | 6 | 0 | 18 | 18 |  6 | 0 |
| INTERSECTION | 12 | 0 | 0 | 12 |  6 |  6 | 0 |

Reading of these numbers, all asserted in the test:

- **Union**: each cube keeps the three quads facing away from the other cube untouched — 3 quads ×
  2 triangles = 6 per cube. The other 24 triangles are pieces the intersection curve cut. Output is
  36 triangles versus the 24 the two inputs had, so faces really were split, not merely relabelled.
- **Difference (A − B)**: A's three far quads survive (6); no whole quad of B lies inside A, so
  `origin B = 0`, but 6 faces still lie on B's surface — the walls of the notch.
- **Intersection**: the shared octant's boundary is entirely cut pieces (`NEW = 12`), split 6/6
  between the two cubes' surfaces, which is the expected three-sides-each of a corner octant.

Every face in every op resolves to a source quad in [0, 6), and the test additionally checks that
each face's centroid lies in the plane of the quad it claims (`assertFacesLieOnTheirSourceQuads`).

## Ticket unknowns, answered

- **"Whether the vendored FFM binding version exposes `faceID` or only `runOriginalID`"** — the
  vendored `ManifoldBindings` wrapper exposes *neither*; its `MeshData64` record carries only
  vertices and triangles. But `libmanifoldc.so` as shipped in `manifold3d-v3.5.1-4.jar` **does**
  export all three C accessors, and `SymbolLookup.loaderLookup()` finds them once the vendored
  binding has loaded the library. No binding regeneration was needed. (The library's own
  "Available Manifold functions" banner printed at load time lists only the subset the vendored
  wrapper binds, which is why it looks as though the symbols are absent — they are not.) `faceId`
  comes back populated: 36 entries for the 36-triangle union.
- **"Whether Manifold's triangulation of coplanar overlaps loses `faceID`"** — it does not lose it,
  but `faceId` is a coplanar-**group** id (one per input quad on this fixture), not a per-triangle
  input index, so a cut face still needs the plane-containment fallback to pick which triangle of
  the group it came from. That fallback is implemented and resolves 100% of faces here.

## Open issues and assumptions

- **`ArrayMesh` has no edge topology.** While restoring the tinting I found that
  `ArrayMesh.edgeCount` is declared but never assigned anywhere in the class, so
  `ArrayMesh.getEdgeIndices()` always returns an empty array and `HalfEdgeMeshRuntime`'s wireframe
  overlay silently draws nothing for any `ArrayMesh`. The first version of the display copy was an
  `ArrayMesh` and lost the scene's wireframe; it is now built with
  `HalfEdgeMesh.bulkAllocate(...)` instead, which restores it. The underlying `ArrayMesh` defect is
  untouched and affects any other caller that uploads an `ArrayMesh` with wireframe on — worth its
  own ticket.
- **Exact-position matching.** Step 3 relies on Manifold copying untouched input vertices with
  bit-identical `double` coordinates. That holds because the operands are handed over as doubles
  and Manifold's exact predicates do not perturb retained vertices. If a future weld pass
  (MESH-50) or a tolerance-based simplify moves them, the untouched/cut split degrades gracefully:
  such a face is classified `ORIGIN_NEW` and still gets its source quad from the `faceId` group, so
  `faceSourceOperand` and `faceSourceQuad` survive — only `faceOrigin` loses precision.
- **The display copy is unwelded.** The scene's tinted mesh has one vertex per corner (108 for the
  36-triangle union), so its wireframe shows every triangle edge twice and all edges register as
  boundary. That is a display artefact of per-vertex tagging only; `MeshBooleanResult.mesh`, which
  is what the node outputs, is unchanged and welded as Manifold produced it.
- **`faceSourceQuad` indexes quads, not triangles**, i.e. it is `QuadTriangulation.triangleSourceFace`
  applied, so a value is a face id in the *input quad mesh*. The test asserts it stays in [0, 6) for
  the cube fixture.
- **`MeshBooleanNode`'s provenance slots changed value type** from raw `int[]` to `IntField`. Only
  `MeshBooleanScene` read them (verified by grep across `src`, `test`, `ixdar_automation_cli`), and
  it was updated. This is the C6 direction, applied to the three slots this ticket owns.
- Three quad-layout test classes fail on the committed tree already (REFACTOR-PLAN-2 A7); not
  touched, not run.
